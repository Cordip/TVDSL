# API парсера Funny и подключение к T0

Публичные объявления и структура узлов: [include/hw2.h](include/hw2.h).
Рабочий потребитель API: [examples/embed.c](examples/embed.c). Он включает только
`hw2.h`, читает Funny из stdin, перечисляет функции и локальные переменные,
обессахаривает обновления массивов и печатает AST.

## Собрать и запустить пример

Команды выполняются из `homeworks/hw2`:

```sh
make build/api-example
./build/api-example < example.funny
```

Начало вывода для этого файла:

```text
Function swap
  Local saved: int
Module @1:1 [#0]
```

Далее идёт дерево с `ArrayUpdate`. Строки `Function`/`Local` получены прямым
обходом `Node*`; они не извлечены из текстового дампа.
Код выхода примера: 0 — успех, 1 — ошибка чтения, создания автомата, разбора или вывода.
При ошибке разбора stdout пуст; диагностика идёт в stderr с путём `<stdin>`.

Для проверки обработки ошибки:

```sh
./build/api-example < tests/cases/missing_semicolon.funny
```

Обе сборки примера проверяются командами `make test` и `make check`; вторая
использует ASan/UBSan. Runner также можно вызвать непосредственно:

```sh
python3 -B tests/run.py ./hw2 tests/examples --api-example ./build/api-example
```

## Подключить исходники к другому C-приложению

Используются C11 и соседняя папка HW1. В команду линковки входят:

- `src/parse/*.c`, `src/ast/*.c` — парсер, адаптер токенов и AST из HW2;
- `../hw1/src/*/*.c` — автомат, лексер и вспомогательные модули HW1;
- include-пути `include`, `src`, `../hw1/include`, `../hw1/src`.

Команда сборки того же примера без Makefile:

```sh
cc -std=c11 -Wall -Wextra -Wpedantic \
  -Iinclude -Isrc -I../hw1/include -I../hw1/src \
  examples/embed.c src/parse/*.c src/ast/*.c ../hw1/src/*/*.c \
  -o /tmp/hw2-api-example
/tmp/hw2-api-example < example.funny
```

В собственном приложении замените `examples/embed.c` своим входным файлом.
CLI-файлы `src/main.c` из HW1 и HW2 не подключаются: `main` принадлежит потребителю.
Указанные шаблоны исходников уже исключают их. Отдельная библиотечная сборка не требуется.

## Путь данных и срок жизни памяти

```text
байты Funny + длина
  → parse_source(automaton, path, input, length, &arena)
  → Module или NULL
  → desugar_module(module, &arena)
  → проход потребителя по Node*
  → arena_free(&arena)
```

1. Получите байты исходника. Пример использует `lexer_read_input` из HW1; допустимо
   передать свой буфер с явной длиной, завершающий NUL не требуется. Для функции
   чтения используйте лимит `HW1_MAX_INPUT_SIZE`: результат 1 означает успех,
   0 — превышение размера, -1 — ошибку чтения; успешный буфер освобождает потребитель.
2. Создайте `Automaton*` через `automaton_build(error, sizeof error)`. При неудаче
   результат `NULL`, причина записана в `error`. Один автомат можно переиспользовать
   для нескольких исходных файлов; завершите работу вызовом `automaton_free`.
3. Создайте обнулённую `Arena arena = {0}`. `parse_source` возвращает исходный AST,
   ещё содержащий `ArrayAssign`. Путь `path` используется в диагностике.
4. Проверьте результат на `NULL`. При ошибке следующий проход не запускается.
   Узлы незавершённого разбора остаются в арене: её освобождают и на этом пути.
5. После возврата `parse_source` исходный буфер можно освободить: имена и числовые
   литералы скопированы в арену. Массив токенов освобождается внутри парсера.
6. Если потребителю нужна нормализованная форма, вызовите `desugar_module`.
   Она меняет AST на месте и выделяет дополнительные узлы в той же арене.
7. Выполните свой проход, пока арена жива. Затем освободите арену и автомат.
   Нельзя вызывать `free` для отдельных узлов или строк. После `arena_free`
   все указатели на них недействительны.

## Как читать AST

- Корень имеет `kind == NODE_MODULE`; `as.module.items` содержит функции и формулы.
  Каждый список обходится через `next` до `NULL` в порядке исходного текста.
- Проверяйте `kind` перед чтением соответствующего поля union `as`. Например,
  `Function` использует `as.function`, `Formula` — `as.formula`, а `Param` и
  `Local` — `as.var_def`. Пример пропускает формулы при перечислении функций.
- Параметры, возвраты, локальные переменные, аргументы и операторы блока — списки.
  `next` связывает элементы списка, а не задаёт универсального ребёнка узла.
- `line` и `column` нумеруются с 1. Новые узлы обессахаривания получают позицию
  присваивания. Целый литерал хранится как десятичная строка без проверки диапазона.
- У параметров и возвратов явный тип. `TYPE_NONE` у локальной переменной означает
  отсутствие аннотации в исходнике; парсер не вывел её тип из присваивания.
- `length` представлен обычным `Call` с именем `length`.
  Пользовательский вызов `set` остаётся `Call`; функциональное обновление массива
  представлено отдельным видом `ArrayUpdate`.

Для `a[i][j] = v` нормализация строит:

```text
a = ArrayUpdate(a, i, ArrayUpdate(Index(a, i), j, v))
```

Здесь `a` и `i` переиспользуются несколькими связями. После нормализации AST может
быть графом с общими узлами. Не изменяйте их, предполагая единственного родителя.
Если проход должен обработать каждый узел ровно один раз, учитывайте посещённые
`Node*`; для аннотаций следующего этапа можно хранить отдельную таблицу по указателю.

## Необязательные поля и значения по умолчанию

Парсер сохраняет факт отсутствия аннотации как `NULL` и не вставляет вместо неё
узел `Bool`. Семантический проход учитывает значения из спецификации Funny:

| Поле исходника | Представление при отсутствии | Семантическое значение |
| --- | --- | --- |
| `requires` | `precondition == NULL` | `true` |
| `ensures` | `postcondition == NULL` | `false` |
| `invariant` | `invariant == NULL` | `true` |

Именно `ensures=false` задано в материалах курса: `funny.ru.md`, раздел
«Пред- и постусловия». Отсутствующая ветка `else` также хранится как `NULL`,
но означает отсутствие оператора, а не логическое значение.

## Ошибки и печать

`parse_source` сначала полностью собирает токены. Первая лексическая ошибка
печатается в stderr и прекращает работу до синтаксического анализа. После
успешной токенизации режим паники позволяет сообщить несколько синтаксических
ошибок. Восстановление может пропустить повреждённый участок; API не обещает
найти каждую ошибку файла. Формат: `path:line:column: error: сообщение`.

При любой ошибке разбора возвращается `NULL`. Список диагностик API не хранит
и не возвращает. Формат восстановления и ограничение глубины описаны в
[grammar.md](grammar.md#ошибки).

`ast_print(output, module, AST_TREE)` печатает дерево с ролями связей, позициями
и ссылками на общие узлы. Отступ ограничен 12 уровнями, затем выводится явная
глубина; узлы при этом не пропускаются. `AST_DOT` печатает DOT-граф с однократным
описанием каждого указателя. Идентификаторы локальны одному дампу, не являются
адресами памяти и не служат ключами между разными форматами или версиями AST.
Схема атрибутов DOT описана в `hw2.h`. Для следующего C-прохода используйте `Node*`.

Потребитель владеет потоком вывода. После печати проверьте `fflush`/`ferror`,
как в примере; `ast_print` не возвращает статус записи.

## Граница T0

Этот компонент предоставляет лексер, разбор, AST и обессахаривание. После
`desugar_module`, пока арена жива, подключается семантический проход T0.
Вывод типов локальных по первому присваиванию ещё не реализован; переменная
без аннотации сохраняет `TYPE_NONE`. Пример подключения не является полным T0.
Сигнатуры текущего API и правила принимаемого языка эта документация не меняет.
